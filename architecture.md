# Digital Twin Bot — ИИ-версия автора для телеграм-канала

Pet-проект на Go: бот, который постит в твой канал контент, сгенерированный моделью, обученной (или "настроенной") на твоих же постах — попытка оцифровать твой стиль письма.

---

## 1. Идея вкратце

1. Собрать историю твоих постов из канала.
2. Построить на их основе "модель стиля" — либо через RAG (few-shot + векторный поиск похожих постов), либо через полноценный fine-tune открытой LLM.
3. Регулярно генерировать черновики новых постов в этом стиле.
4. Пропускать их через шаг модерации (ты одобряешь/правишь), прежде чем публиковать от своего имени.
5. Публиковать в канал по расписанию.

Ключевой принцип: **никогда не публиковать без review**, пока не будет накоплена уверенность в качестве модели — это твой личный бренд, и галлюцинации/ляпы туда лучше не пускать.

## 3. Компоненты подробно

### 3.1 Data Collector
Для **новых** постов ничего специального делать не нужно: если бот добавлен админом в канал, Telegram Bot API сам присылает апдейт `channel_post` на каждый опубликованный пост — сбор в обучающий корпус происходит автоматически, в реальном времени (детали — в разделе 10).

Для **исторических** постов (всё, что было до подключения бота) нужен один из вариантов, но это разовая операция:
- **Ручной экспорт** через Telegram Desktop (Chat → Export chat history → JSON) — самый простой старт.
- **MTProto-клиент на Go** (библиотека `gotd/td`) под твоим личным аккаунтом — умеет читать всю историю программно.

Собранные данные: текст поста, дата, медиа-ссылки, просмотры/реакции (если есть) — реакции потом пригодятся для оценки "какой стиль заходит лучше".

### 3.2 Post Store
Postgres как основное хранилище. Если пойдёшь по пути RAG — плюс `pgvector` (или отдельный Qdrant/Weaviate) для эмбеддингов постов.

### 3.3 Style Model — два пути

**Вариант A: RAG / few-shot (рекомендую начать с этого)**
- Не требует GPU и обучения.
- Эмбеддинги постов складываются в векторную БД.
- При генерации нового поста подтягиваются N наиболее похожих/репрезентативных твоих постов и подмешиваются в промпт как few-shot примеры + инструкция "пиши в этом стиле".
- Генерация — через любой LLM API (OpenAI, Anthropic, или локально через Ollama).
- Быстрый старт, дёшево, легко итерировать на промпте.

**Вариант B: Fine-tuning**
- LoRA-дообучение открытой модели (Mistral/Llama и т.п.) на корпусе твоих постов.
- Дообучение обычно делается не на Go, а через Python-экосистему (PEFT/unsloth/axolotl) или managed fine-tuning API (OpenAI fine-tuning, Together.ai). Go в этом варианте выступает оркестратором — вызывает inference-сервер (vLLM / text-generation-inference) или API готовой fine-tuned модели.
- Даёт более "родной" стиль, но требует: заметного объёма данных (обычно от нескольких сотен постов для внятного результата), GPU-ресурсов и больше времени на итерации.

**Рекомендация**: старт с варианта A, миграция на B, когда накопится достаточно данных и станет ясно, что few-shot упирается в потолок качества.

### 3.4 Generator Service
Go-сервис/пакет, который собирает промпт (инструкция стиля + few-shot примеры из RAG) и дёргает LLM API, возвращая черновик поста.

### 3.5 Moderation (важный шаг!)
Прежде чем публиковать от своего имени, черновик уходит тебе в личку/админ-чат с inline-кнопками **Approve / Edit / Reject**. Публикация в канал происходит только после одобрения. Это защищает от фактических ошибок и "не твоих" по духу постов, особенно на старте, пока модель ещё сырая.

### 3.6 Scheduler / Publisher
Cron-задача (например, `robfig/cron`) генерирует черновик N раз в неделю по расписанию → отправляет на модерацию → после approve публикует через Telegram Bot API (бот должен быть админом канала).

### 3.7 Observability
Логи, базовые метрики (например Prometheus), алерты на сбои генерации или публикации.

## 4. Технологический стек

| Слой | Технология |
|---|---|
| Язык | Go 1.22+ |
| Telegram Bot API | `go-telegram-bot-api/telegram-bot-api` или `tucnak/telebot` |
| Сбор истории канала | `gotd/td` (MTProto) или ручной экспорт из Telegram Desktop |
| LLM / эмбеддинги | OpenAI / Anthropic API, либо локально через Ollama |
| Векторный поиск (для RAG) | Postgres + `pgvector`, либо Qdrant |
| Основное хранилище | PostgreSQL |
| Планировщик | `robfig/cron` |
| Деплой | Docker + docker-compose, VPS |

## 5. Схема данных (пример)

```sql
-- Собранные исходные посты
CREATE TABLE posts (
    id            BIGSERIAL PRIMARY KEY,
    tg_message_id BIGINT UNIQUE,
    text          TEXT NOT NULL,
    posted_at     TIMESTAMPTZ,
    views         INT,
    reactions     JSONB,
    media_urls    TEXT[]
);

-- Эмбеддинги для RAG
CREATE TABLE post_embeddings (
    post_id   BIGINT REFERENCES posts(id),
    embedding VECTOR(1536)
);

-- Сгенерированные черновики и их судьба
CREATE TABLE generated_posts (
    id           BIGSERIAL PRIMARY KEY,
    draft_text   TEXT NOT NULL,
    status       TEXT CHECK (status IN ('draft','approved','edited','rejected','published')),
    created_at   TIMESTAMPTZ DEFAULT now(),
    published_at TIMESTAMPTZ,
    source_posts BIGINT[] -- какие посты были использованы как few-shot примеры
);
```

## 7. Пайплайн по шагам

1. Экспорт истории канала (вручную или через MTProto-коллектор).
2. Импорт постов в Postgres.
3. (Для RAG) Генерация эмбеддингов и заливка в векторное хранилище.
4. По расписанию: построение промпта (инструкция стиля + релевантные few-shot примеры).
5. Генерация черновика через LLM.
6. Отправка черновика тебе в личку на модерацию.
7. После Approve — публикация в канал; после Reject — лог причины (полезно для доработки промпта).
8. Постепенное пополнение базы новыми постами (в том числе одобренными сгенерированными — с осторожностью, чтобы не "зациклить" стиль).

## 8. Roadmap

**MVP (1–2 недели)**
- Разовый бэкфилл истории (экспорт из Telegram Desktop).
- Бот-админ в канале: real-time приём новых постов через `channel_post`, автосохранение в БД.
- Простой few-shot без векторной БД (случайные 5–10 примеров из истории).
- Cron-генерация черновика по расписанию → push тебе в личку с кнопками «Опубликовать / Редактировать / Отклонить» → публикация после апрува.

**V2**
- Векторный поиск релевантных постов (pgvector/Qdrant) вместо случайной выборки.
- Флаг `is_generated` — исключение сгенерированных постов из обучающего корпуса.
- Учёт реакций/просмотров как сигнала качества.

**V3 (опционально)**
- LoRA fine-tune на открытой модели.
- A/B тестирование разных промптов/моделей стиля.

## 9. Риски и что учесть

- **Telegram ToS**: сбор истории через MTProto под личным аккаунтом делать аккуратно, без агрессивного массового парсинга.
- **Галлюцинации модели**: обязателен человеческий review, особенно если в постах есть факты, даты, цифры.
- **Rate limits** Telegram Bot API при публикации.
- **Хранение секретов**: API-ключи LLM и Telegram — через переменные окружения/secret-manager, не в репозитории.
- Стиль без review может со временем "заэхо-камериться", если сгенерированные посты сами становятся источником для будущих few-shot примеров — стоит помечать их отдельно и ограничивать долю в выборке.

## 10. Полная автоматизация: real-time pipeline

### Автоматическая загрузка новых постов в корпус
Если добавить бота админом в канал, Telegram Bot API сам присылает боту апдейт `channel_post` на каждый новый пост в канале — в реальном времени, без ручного экспорта. Дальше всё просто:

1. Апдейт приходит боту → текст поста сохраняется в `posts`.
2. Сразу генерируется эмбеддинг → добавляется в векторную БД.
3. Корпус для RAG растёт сам по себе с каждым твоим новым постом.

Ручной экспорт (Telegram Desktop / MTProto) нужен тогда только один раз — чтобы забутстрапить историю до момента, когда бот стал админом.

**Важный нюанс**: сгенерированные ботом посты тоже прилетят как `channel_post`, раз публикуются в тот же канал — их нужно помечать флагом `is_generated = true` и исключать из обучающего корпуса. Иначе стиль начнёт «эхо-камериться» сам на себе, и модель постепенно будет обучаться на своих же черновиках, а не на твоём реальном голосе.

### Уведомление и одобрение "на бегу"
Telegram сам по себе — уже готовая система push-уведомлений, отдельная инфраструктура не нужна:

1. По расписанию (cron) генерируется черновик.
2. Бот присылает его тебе в личку с inline-кнопками: **✅ Опубликовать / ✏️ Редактировать / ❌ Отклонить**.
3. Прилетает как обычное уведомление на телефон — тапнул «Опубликовать» сидя на паре, боту приходит callback-запрос, он публикует пост в канал через `sendMessage`/`copyMessage`.
4. «Редактировать» — бот просит прислать исправленный текст ответом на сообщение, показывает обновлённые кнопки для финального подтверждения.

Всё происходит без какого-либо веб-интерфейса — только Telegram, и это уже полностью закрывает сценарий «увидел уведомление на паре → одобрил с телефона».

### Технические детали для real-time режима
- Бот должен быть **админом** канала — иначе `channel_post` апдейты не приходят вообще.
- Апдейты можно получать через **long polling** (`getUpdates`) — не нужен публичный HTTPS-сервер, отлично подходит для pet-проекта на обычном VPS без домена и сертификатов.
- Либо через **webhook**, если важна минимальная задержка — тогда нужен публичный HTTPS-эндпоинт (VPS + Let's Encrypt, или туннель вроде Cloudflare Tunnel на этапе разработки).
- Процесс должен работать постоянно (systemd-сервис или Docker-контейнер с restart-policy) — иначе апдейты при полинге будут пропущены, пока бот не работал.
